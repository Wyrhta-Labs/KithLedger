# Access control in KithLedger (B4–B9)

The implementation-level companion to
[ADR 0004 — per-member access control in the knowledge graph](https://github.com/Wyrhta-Labs/wyrhta/blob/main/docs/decisions/0004-per-member-access-control-in-the-knowledge-graph.md)
and [ADR 0009 — satellite token exchange](https://github.com/Wyrhta-Labs/wyrhta/blob/main/docs/decisions/0009-satellite-token-exchange.md).
The ADRs record *what was decided and why*; this file records *how it is built here* and
which invariants a change must not break.

`AGENTS.md` carries the short form of these rules. **Read this file before touching
`src/services/scope.ts`, graph traversal, member provisioning, or offboarding** — several
of the invariants below are the kind that a locally reasonable edit silently breaks
(filtering a CTE's output instead of its terms, dropping a `visibility = 'shared'` guard,
backfilling a provenance column).

## Household members (JIT provisioning, B4)

members are authored in Heorth ALONE — no roster, no sync, no provisioning route. The first request carrying a verified token for an unseen `sub` creates the local record (`src/services/members.ts`), a row in core's `users` table **whose id IS the `sub`**, plus a `household_members` row recording Heorth provenance. Reusing `users` (rather than a separate member table) is what lets ADR 0004 / B5's `owner` columns foreign-key ONE table and cover the local admin too; the synthesised `email`/`handle` are derived from the `sub` (`.invalid` domain, `heorth-` prefix) and the `password_hash` is a non-argon2 sentinel, so **a member can never log in locally**. `requireLocalAccount` additionally keeps members off the long-lived `kl_` key routes. Role comes from the token every request and is never elevated; `users.role` is a mirror kept in step with the last token seen. An unknown role or a non-uuid `sub` is refused (401), as is a `sub` colliding with a locally authored account. **Both rows are written by ONE statement** — a CTE whose `household_members` insert selects from the `users` insert's `RETURNING` — so the pair is never separately observable: a `users` row without provenance is a local account, never a half-provisioned member (as two statements made it, refusing a member's concurrent first requests with a 401), and provenance can only be stamped on a row that statement itself created, so a local account cannot be adopted even if it appears mid-flight. A losing concurrent request needs no retry: its `ON CONFLICT DO NOTHING` waits on the winner's unique-index entry and reads the committed result. The already-provisioned hot path is a single joined read.

## Per-member visibility, enforcement and traversal (B5 schema, B6, B7)

every node (`people`) and every edge (`interactions`, `relationships`, `reminders`) carries `owner_id` (FK `users.id`, `ON DELETE RESTRICT` — offboarding must reassign, never cascade) and `visibility` (`private` | `shared` | `household`, CHECK-constrained, defaulting to `household`). `household` is an explicit state, **not** a share list containing every member, so new members see household items automatically and `shared` subsets never silently grow. The `shared` set lives in four per-entity tables (`person_shares`, `interaction_shares`, `relationship_shares`, `reminder_shares`), composite PK `(entity_id, member_id)`, both sides foreign-keyed. **Enforcement (B6, ADR 0004 §2 + §4):** `src/services/scope.ts` is the ONE place the read predicate exists — `visibleTo(entity, scope, alias?)` emits `visibility = 'household' OR owner_id = :me OR (visibility = 'shared' AND EXISTS <share>)` for any table and any alias, and every list, get, count and existence pre-check in `src/services/` applies it. Never consult a share table without the `visibility = 'shared'` guard: grants outlive a `shared` -> `private` flip, so dropping it is a permanent leak. Counts reuse their rows' `where` (a total of 5 when you see 3 is a leak). Out-of-scope items are 404, never 403 (§3.1). Routes resolve `c.get('principal')` to a `Scope` and pass it as the first service argument; they still never touch Drizzle. Writes stamp `owner_id` from the principal (NOT NULL as of migration `0005`); `visibility` and the `sharedWith` set are owner-only (§4, sharing is not transitive), content edits deliberately follow read scope. `role === 'admin'` is never consulted — there is no god-mode to bypass with. `HOUSEHOLD_SCOPE` expresses the always-on dashboard's read-only `household`-only scope (§2.2); B8 gives it a credential (below). **Traversal (B7, ADR 0004 §3):** `getPersonGraph(scope, personId, depth)` applies the same `visibleTo` at every hop. An edge is returned only when its own row is visible AND both endpoints resolve to a visible person (`visibleTo` is per-row; the endpoint `EXISTS` conjuncts are separate, because §1 makes edge visibility independent of its endpoints). That combined fragment sits in the depth-1 `where`, in the recursive CTE's base term AND in its recursive term — which is what stops pass-through: every row in the CTE has two visible endpoints, so the recursion can only pivot on already-visible nodes and `You -> [hidden] -> Cousin` has no second hop, while an independent visible path to Cousin still works. Filtering the CTE's OUTPUT would traverse the hidden node first and surface Cousin; `DISTINCT ON (id)` runs after traversal, so anything applied there is too late. Node hydration is a separate query and re-applies the predicate — filtering only edges hydrates hidden people's names, filtering only nodes leaves edges naming hidden ids. An invisible root 404s exactly as a non-existent one does.

## Three principals, three separate credentials (B8, ADR 0004 §2)

a `kl_` key carries a `kind` — `member` | `household` | `ops` — in `api_key_credentials` (a KithLedger-local side table keyed by `api_keys.id`, because `api_keys` is core's and shared by every service). The kind is decided ONCE, at authentication, from the credential itself and never from the request: `resolveApiKey` reads the stored row, and every JWT is a member principal by construction (the only two this service accepts are the local HS256 admin token and a Heorth member token, whose claims ADR 0009 fixes to `sub` + `role`). `scopeFor(principal)` is the single mapping — member → `memberScope(userId)`, household → `HOUSEHOLD_SCOPE` (the key owner's `userId` is deliberately DISCARDED, or a leaked dashboard key would read as that account's personal scope), ops → throws `NO_DATA_ACCESS`. `requireDataAccess` guards all four domain routers plus the graph route: an **ops** credential is refused outright (403 — about the whole resource, so it discloses nothing about any item, unlike §3.1's per-item 404), and a **household** credential is refused any non-GET, which is every mutation in the service in one rule; `ownerFor()` refuses the same write one layer down because a member-less scope has no `owner_id` to stamp. A key with **no** `api_key_credentials` row is refused (401) rather than read as a member key — losing a row must narrow a credential to nothing, never widen a household key to a member's full scope. Migration `0006` backfills every pre-B8 key as `member`, so keys minted before B8 (Heorth's `KITH_API_KEY` among them) are unchanged. `POST /auth/keys` takes an optional `kind` (default `member`) and is JWT + local-account only, so no key of any kind can mint a key.

## Provenance, delete policy and offboarding (B9, ADR 0004 §4)

every domain row also carries `updated_by` (FK `users.id`, **`ON DELETE SET NULL`** — it is provenance, not ownership, so unlike `owner_id` it must never veto a lifecycle operation, and a departing writer leaves NULL = "not recorded" rather than a reattribution). It is stamped from the acting principal wherever `owner_id` is stamped from `ownerFor(scope)` — including snooze/dismiss/complete, and on a recurring reminder's successor row, where `owner_id` is inherited from the original but `updated_by` is whoever ticked the box. Migration `0007` deliberately backfills NOTHING: `updated_by = owner_id` would assert the very claim the column exists to disprove, and the pre-B9 rows span the pre-member and member-writes eras. **Delete is narrower than read and than edit:** `household` items stay deletable by any member (B6's argument — the default state must not be read-only for everyone but its author — applies most strongly there), but a `private` or `shared` item is **owner-only** to delete; content edits are unchanged. `deletableBy`/`canDelete` in `scope.ts` are the one rule in its two renderings (pre-check → 403 `NOT_OWNER`, plus the same predicate on the DELETE statement so a visibility flip cannot race it); an item outside the scope still 404s. **Offboarding** (`src/services/offboarding.ts`, `GET`/`POST /api/v1/members/:id/offboarding`) is what makes `owner_id`'s RESTRICT resolvable: `ownerOnlyItems: 'reassign' | 'delete'` (no default — the ADR wants a decision, not a fallback) plus a `successorId`. `private`/`shared` items follow the decision; `household` items are ALWAYS reassigned, never deleted. **No standing god-mode:** nothing in the flow SELECTs content — every statement is an `UPDATE`/`DELETE` with no `RETURNING` plus one `SELECT EXISTS`, and the only thing exposed is the single boolean `hasOwnedItems`, which the RESTRICT error already discloses; no counts (§3.4), no per-table breakdown, nothing per-item. Owner-only items may only be reassigned to a current **Heorth-authored** member, so the operator cannot name their own account and read them. The gate is `requireJwt` + `requireLocalAccount` (as `/auth/keys`): none of B8's three `kl_` kinds and no member can invoke it, and `role` is never consulted. Grants to the departing member and their `household_members` row cascade with the `users` delete; a reassigned item keeps its share set. KithLedger keeps no roster and no denylist (ADR 0007), so **remove the member in Heorth first** or they are re-provisioned on their next token.
